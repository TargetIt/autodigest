# Auto Digest 工作流

当一个复杂概念、复杂系统、技术方案、产品能力或知识点需要被消化时，使用这个工作流。

目标是：先产出一篇真正讲清楚的核心解释，再用例子、反例、追问和少量高价值视角扩展它。不要把“形式完整”误认为“理解完成”。

## 不可违反的规则

- 不编造事实、历史、机制、数据、人物、名称或因果关系。
- 明确区分：原文事实、解释、类比、推测和外部补充。
- 即使用通俗语言，也必须保持原理不变形。
- 优先使用具体例子，不堆抽象形容词。
- 资料不足时，必须标注为“待确认”或“开放问题”。
- 每个视角都必须服务于同一个对象，不能写着写着偏到另一个话题。
- 不为了填满模板而硬套视角；不能提供新增理解的视角应跳过。
- 检视发现的问题必须先修复，再进入最终沉淀和提交推送。

## 输入信息

写作前先收集：

- 待消化对象：
- 原始材料：
- 读者是谁：
- 期望输出：
- 已知约束：
- 我当前的问题：

## 阶段 1：定义对象与资料边界

先写一个中性定义：

- 它是什么？
- 它解决什么问题？
- 它的边界内包含什么？
- 它的边界外不包含什么？
- 什么解释会把它讲错？

然后说明资料边界：

- 哪些内容直接来自原始材料？
- 哪些是解释、类比或推导？
- 哪些需要外部资料才能确认？
- 哪些内容不能编造？

## 阶段 2：建立源信息账本

把原始材料拆成可核对的信息单元，并记录原文位置：

- 事实与数据。
- 作者的主张与结论。
- 机制与因果关系。
- 定义与关键术语。
- 例子与反例。
- 条件、边界与例外。
- 不确定性、保留意见与开放问题。
- 原文给予各项内容的强调程度和证据强度。

每个信息单元必须有唯一编号，并标出它是否进入核心解释。不能只摘录支持当前理解的内容，也要记录冲突信息、限制条件和原文没有解决的问题。

## 阶段 3：理解诊断

在写长文前，先找出真正影响理解的地方：

- 最容易被误解成什么？
- 原文在哪些地方跳步？
- 哪些术语被当成答案，但其实还没有解释机制？
- 哪些前提是隐含的？
- 哪些边界条件会改变结论？
- 哪个例子最能让机制可见？
- 哪个反例最能说明它不是什么？

这一步的产物是 3-7 个理解难点。后续核心解释必须逐项处理这些难点。

## 阶段 4：核心解释

先只写一篇核心解释，不写十篇文章。

核心解释至少回答：

- 这个对象解决什么核心问题？
- 如果没有它，会遇到什么基础矛盾或能力缺口？
- 它由哪些必要部分组成？
- 这些部分按什么顺序交互？
- 输入是什么，输出是什么？
- 最小例子是什么？
- 它不是什么？
- 它在哪些条件下不成立？
- 哪些内容来自原文，哪些是解释或推导？

判断标准：

- 一个聪明但不熟悉该主题的人，读完能复述机制。
- 解释中没有用术语替代机制。
- 例子能够跑通关键过程。
- 边界和限制条件没有被省略。

## 阶段 5：最小例子

设计一个最小但完整的例子，从输入到输出跑通一次，让复杂系统的核心机制可见。

例子必须说明：

- 它要展示的机制。
- 输入、组件、状态变化和输出。
- 每一步发生了什么。
- 每一步对应核心解释中的哪个环节。
- 这个例子省略了什么。
- 为什么这些省略不会歪曲核心原理。

如果当前材料不足以构造例子，必须标注为“待确认”，不能编造关键过程。

## 阶段 6：误解与反例

用反例校准解释边界。

至少处理：

- 它最容易被误解成什么？
- 这种误解为什么有诱惑力？
- 它错在哪里？
- 哪个反例能说明这种误解不成立？
- 哪些条件改变后，原解释需要修改？
- 哪些结论只能在特定范围内成立？

反例不是装饰。反例的作用是防止核心解释讲过头。

## 阶段 7：追问修复

用连续追问暴露解释缺口：

- 为什么？
- 为什么这一步能成立？
- 如果输入改变会怎样？
- 如果某个条件缺失会怎样？
- 有没有一个新例子可以独立验证？
- 它失败时是什么样？

对每个缺口记录：

- 卡住的位置。
- 缺口类型：跳步、术语依赖、循环定义、无依据断言、边界缺失、例子不足。
- 回到哪条源信息或哪部分材料修复。
- 修复后的新解释。
- 仍未确认的问题。

## 阶段 8：可选视角扩展

十个视角是工具箱，不是必填项。每次只选择能带来新增理解的 2-4 个。

生成视角文章前，先做适用性判断：

| 视角 | 适用条件 | 是否选择 | 理由 |
| --- | --- | --- | --- |
| 第一性原理 | 能从基础约束和需求推导对象 |  |  |
| 客户需求 | 有明确用户、痛点和成功标准 |  |  |
| 生活化类比 | 能找到不歪曲机制的类比 |  |  |
| 历史发展 | 有可靠历史资料支持 |  |  |
| 层次化系统 | 对象有清晰层次、模块和接口 |  |  |
| 控制论 | 有目标、控制者或可操纵条件 |  |  |
| 信息论 | 信息源、信号、通道、接受者清晰 |  |  |
| 最小 Demo | 可以进一步扩展可运行例子 |  |  |
| 数据结构 | 能自然抽象为元素和关系 |  |  |
| 费曼式消化 | 需要记录学习缺口和回源修复 |  |  |

被选择的视角必须说明它相对核心解释新增了什么。被跳过的视角必须说明跳过原因。

## 阶段 9：检视

检视对象包括：

- 源信息账本。
- 核心解释。
- 最小例子。
- 误解与反例。
- 追问修复。
- 可选视角扩展。
- 最终输出草稿。

### 源材料忠实度检视

从源材料到产出：

- 关键事实、主张、机制、数据、例子、条件、例外和不确定性是否进入核心解释？
- 没有进入产出的内容是主动取舍，还是意外遗漏？
- 原文重点是否被弱化，次要内容是否被放大？
- 原文的“可能”“相关”“在特定条件下”是否被升级成“必然”“因果”“普遍成立”？
- 信息是否脱离原来的前提、范围、时间、对象或上下文？

从产出回到源材料：

- 新增内容属于解释、推导、类比、推测、外部事实还是作者判断？
- 新增内容是否有依据，是否明确标注？
- 为了连贯而补出的因果关系、时间顺序或动机，原文是否真的支持？
- 改写是否改变了主语、对象、范围、程度、证据强度或确定性？

### 质量检视

- 核心解释是否回答了对象解决什么问题？
- 是否讲清了机制，而不是复述术语？
- 最小例子是否跑通关键过程？
- 反例是否真正校准边界？
- 追问是否暴露并修复了理解缺口？
- 可选视角是否带来新增理解，而不是重复核心解释？

### 一致性检视

- 核心解释、例子、反例和视角扩展是否讲的是同一个对象？
- 同一概念、数字、流程、边界在各文件中是否一致？
- 类比是否引入错误机制？
- Demo 是否支撑核心解释？
- 可选视角里的承诺是否被源材料或核心模型支持？

## 阶段 10：最终沉淀与提交

最后创建或更新：

- 可复用概念页。
- `digests/<主题>/` 中的源账本、核心解释、例子、反例、追问修复、可选视角扩展、检视记录和最终输出草稿。
- 如需对外发布或复用，再将整理后的最终文章、学习指南、图解或演讲稿放入 `outputs/`。
- 开放问题列表。

提交前必须确认：

- 重要源信息都有明确去向。
- 未确认信息已经明确标注。
- 视角扩展没有硬套。
- 检视发现的问题已经处理或记录为开放问题。
- 只提交本次消化相关文件，不混入无关变更。
- 提交后推送到远端仓库。

## 方法来源说明

控制论与信息论两个可选视角主要借鉴金观涛、华国凡《控制论与科学方法论》第一章“控制和反馈”和第二章“信息、思维和组织”，并转换成适合 Auto Digest 的提问框架。书中的“可能性空间”“共轭控制”等表述包含作者自己的方法论创造，与西方控制理论、维纳控制论或香农信息论不完全等同；使用时必须注明这是本书启发下的定性方法，不能把它们混写成所有学派一致接受的严格定义。
